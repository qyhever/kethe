# 登录设备管理实现方案

## 范围与已确认规则

- 用户可以在「我的 → 设置 → 账号与安全 → 登录设备」查看当前账号的有效登录会话，并让指定设备退出。每次成功登录创建一条会话，同一台设备使用不同浏览器登录可能产生多条记录。
- 新会话被撤销后，目标客户端的下一次受保护请求会收到 `401`，刷新令牌也随即失效。目标客户端通过现有认证流程回到登录页。
- 上线前签发、没有 `sid` 的访问令牌和刷新令牌继续按其自身有效期使用。旧会话无法在列表中标记为当前设备，也无法远程撤销，用户重新登录后纳入管理。
- 修改密码和通过邮箱验证码重置密码均沿用现有行为，已有令牌和会话继续有效。

## 数据库与认证

1. 在 `kethe-backend/sql/init.sql` 添加 `auth_sessions`，同时新增 `kethe-backend/sql/2026-11-18-device-manage.sql` 供已有数据库升级。表字段包括随机 UUID `id`、与 `users.id` 同类型的 `user_id`、`refresh_jti`、`device_label`、`created_at`、`last_active_at`、`expires_at` 和 `revoked_at`。为 `id` 建主键，为按用户查询有效会话建立索引，并按现有建表规范处理用户外键。
2. 在认证模块注册 TypeORM 实体和会话服务。`AuthController` 将登录请求的 `User-Agent` 传给 `AuthService`，生成长度受限的设备描述，如「iPhone · Safari」。无法识别时显示「未知设备」。设备描述仅用于展示，身份与归属由 `sid` 和 `user_id` 判定。延用现有企业微信登录通知，设备列表仅返回所需的展示字段。
3. 登录通过邮箱、密码和账号状态校验后创建会话。两枚 JWT 共用同一个 `sid`，各自保留独立 `jti`。会话有效期以当前刷新令牌的 `exp` 为准，成功刷新时按现有 `JWT_REFRESH_EXPIRE` 配置续期。会话落库成功后才返回令牌。
4. 新令牌刷新时验证 JWT、账号状态及会话有效性，以 `sid`、`user_id`、当前 `refresh_jti`、未撤销和未过期为条件原子更新刷新凭据及过期时间。仅更新成功的请求返回新令牌，旧刷新令牌无法再次换取令牌。刷新和撤销竞争时，撤销完成后该会话签发的令牌均无法继续使用。
5. `AccessTokenGuard` 保留现有 JWT 校验，并对带 `sid` 的令牌按会话 ID 和用户 ID 查询 MySQL。会话不存在、已撤销或已过期时返回 `401`。通过校验后在 `RequestWithContext.user` 中提供可选的 `sessionId`，供当前设备标记和登出使用。最近活跃时间按会话节流更新，建议同一会话五分钟内最多写一次。
6. 旧令牌沿用独立兼容分支。仅在校验通过且确实没有 `sid` 时进入该分支，格式非法的 `sid` 按认证失败处理。旧访问令牌直接使用到自身 `exp`。旧刷新令牌在自身 `exp` 前可换取不带 `sid` 的访问令牌，其到期时间取访问令牌配置期限和旧刷新令牌剩余期限中的较短者。刷新响应原样返回该旧刷新令牌，使兼容期限有明确上限。

## 接口

三个接口均放在 `AuthController`，沿用现有访问令牌守卫、Swagger 声明和响应包装。下表使用后端 `/api` 路径，H5 通过现有请求层调用 `/auth/...`。

| 接口 | 请求与响应 |
| --- | --- |
| `GET /api/auth/sessions` | 返回 `{ currentSessionId, sessions }`。列表项包含 `id`、`deviceLabel`、`createdAt`、`lastActiveAt`，当前会话置顶，其余按最近活跃时间倒序。旧会话的 `currentSessionId` 为 `null`，仍可查看并撤销账号下已纳入管理的会话。 |
| `DELETE /api/auth/sessions/:id` | 校验 UUID，并按当前用户限定更新范围。已撤销、过期、无此记录或不属于当前账号时统一返回包装后的成功 `null`。当前会话由专用登出接口处理，对当前会话 ID 的删除请求返回业务错误。 |
| `POST /api/auth/logout` | 按当前用户和 `sid` 撤销当前会话，返回包装后的成功 `null`。无 `sid` 的旧访问令牌调用时也返回成功，由客户端清理本地状态。 |

## H5 页面与请求层

1. 在 `SettingsPage.tsx` 的「账号与安全」菜单添加「登录设备」，在 `App.tsx` 的 `RequireAuth` 下注册 `/profile/settings/security/devices`，复用 `SettingsHeader`、Dialog 和 Toast。设备列表支持加载、失败后重试和空状态。当前设备置顶并标记「当前设备」，其余设备经二次确认后退出。旧会话访问时提示「本次登录暂未纳入设备管理，重新登录后可显示」。
2. 在 `src/api/auth.ts` 和对应类型中接入会话 API。将 `ProfilePage.tsx` 的主动退出与被动 `401` 清理分开。主动退出先请求服务端，成功或确认会话已失效时清理本地状态。遇到网络或服务端错误时保留当前登录状态并提示重试。被动失效直接清理本地状态，避免再次发起登出请求。
3. 在请求层把刷新结果与发起时的登录状态绑定。只有本地仍持有对应会话的刷新令牌时才写入结果，避免迟到响应覆盖退出、重新登录或其他标签页更新后的状态。刷新失败时也应先检查本地凭据是否已经被替换，再决定是否清理会话。
4. 多标签页共用 `localStorage`。优先协调同源标签页刷新，在获得锁后重新读取令牌，已有新令牌时直接复用。服务端只允许一次轮换成功。并发失败的标签页在有限时间内等待读取其他标签页写入的新令牌，再重试原业务请求一次。轮换成功但响应丢失，且没有标签页拿到新凭据时，引导用户重新登录。

## 实施与验收

1. 先完成 SQL、TypeORM 实体、JWT 会话关联和撤销逻辑，再接入接口及 Swagger，最后实现 H5 页面、主动登出和刷新协调。部署前先应用数据库升级脚本，并协调前后端发布窗口。
2. 后端验证同账号多会话、不同账号隔离、当前会话标记、重复撤销、自身退出、撤销后的访问和刷新、刷新并发与撤销竞争。准备上线前格式的 JWT，覆盖旧访问令牌和旧刷新令牌的有效期边界，验证旧刷新不会延长兼容期限。覆盖修改密码和邮箱重置后原会话继续有效。
3. 使用两个浏览器或独立浏览器配置验证远程退出，再用同源多标签页验证并发刷新、退出后迟到响应、退出失败重试和重新登录。检查列表加载、空状态、失败重试和移动端确认弹窗。
4. 实现后执行 `pnpm -C kethe-backend lint`、`pnpm -C kethe-backend build`、`pnpm -C kethe-backend test --runInBand`、`pnpm -C kethe-backend test:e2e --runInBand`、`pnpm -C kethe-frontend-h5 lint` 和 `pnpm -C kethe-frontend-h5 build`。检查后端 lint 自动修复及构建生成的 `public/meta.json` 差异，避免纳入无关变更。
